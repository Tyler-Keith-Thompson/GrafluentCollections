Persistent trees

How do you keep every version of a set without copying it for each edit?

Example: inserting 7 into a set of fourteen numbers makes version 1. It has five new vertices, the path from the root down to where 7 goes. Its other ten vertices are the very ones version 0 holds, and version 0 still reads as it did.

What it’s forUndo, snapshots and safe sharing

A persistent structure never changes a version once it exists: an edit returns a new version, and the old one stays readable. That gives undo and history for free, lets a reader keep a consistent snapshot while a writer moves on, and makes sharing across threads safe without locks. Functional languages build their maps and sets this way, and so do editors, version-control internals and databases that offer snapshots.

The ideaCopy the path, share the rest

In a search tree, an edit only changes the vertices on the path from the root to the change. So the new version copies just that path, with each copy pointing at the old version’s untouched subtrees, and a rebalance copies the few vertices it rotates. Each edit costs O(log n) new vertices, and a history of n edits takes O(n log n) space in all, not a whole tree per version.

GrafluentCollections balances by weight (Adams, 1993): no subtree holds more than three times its sibling’s elements. elementsInSharedVertices(with:) names the vertices two versions hold in common, and BinaryTree(version) gives each version’s shape.

Where it breaksMany small allocations

Every edit allocates new vertices, and every vertex is a separate object, so a set that is only ever used in its latest version is faster as an ordinary sorted array or a mutable tree that changes in place. Versions also keep each other’s vertices alive, so holding on to old versions holds their memory.
