B-trees

How do you keep a sorted set shallow when every step down costs a trip to memory?

Example: insert 10 to 70 in steps of 10, then 25, 35, 45 and 55. The eighth key overfills the root, which splits around 40: 40 becomes the new root over two leaves, and the tree gains its second level at the top.

What it’s forSorted keys, few steps down

A B-tree keeps keys in order like a balanced binary tree, but each node holds many keys in a row. A search reads one node per level and finds its way inside the node with a short scan, so it visits far fewer nodes than a binary tree, and each node it reads is one contiguous block. That suits caches in memory as much as blocks on disk. Ordered scans and range queries walk whole nodes at a time.

The ideaSplit when full, merge when thin

Every node but the root holds between t − 1 and 2t − 1 keys, and a node with k keys has k + 1 children, one for each gap. Every leaf is at the same depth. A new key goes into its leaf. If the leaf was already full, it splits into two around its middle key, and the middle key moves up into the parent, which may split in turn. When the root splits, its middle key becomes a new root, and that is the only way the tree grows taller.

Removing a key from a leaf can leave the leaf one key short. It borrows a key through the parent from a sibling that can spare one, or else merges with a sibling, taking the key between them down from the parent. A key in an inner node is replaced by the key just before it, taken from a leaf. Bayer and McCreight described the tree in 1970.

GrafluentCollections sizes nodes in bytes, about 512 bytes of elements each, so the number of keys per node depends on how large the elements are. The table above keeps a 64-byte row per key, which makes t = 4: from 3 to 7 keys per node. With 8-byte integer keys alone, a node holds up to 63.

Where it breaksMoving keys within a node

Inserting into or removing from a node shifts the keys after it, so a single update costs time in proportion to the node’s size, not just the depth. When updates far outnumber reads and scans, a red–black tree moves less. Keeping many versions of the set calls for a persistent tree instead, which shares unchanged nodes between versions.

In SwiftThe operations above, in GrafluentCollections

import BTrees
import Trees

/// A row of 64 bytes. A B-tree sizes its nodes in bytes, so with rows this large a node holds
/// at most 7 keys, and a few dozen keys already make several levels.
struct Row {
    var fields: (Int64, Int64, Int64, Int64, Int64, Int64, Int64, Int64) = (0, 0, 0, 0, 0, 0, 0, 0)
}

let operations = [10, 20, 30, 40, 50, 60, 70, 25, 35, 45, 55, 65, 5, 15, 75, 80, -40, -45, -50, -35, -30, -25, -20]  // negative: remove

var table = BTreeDictionary<Int, Row>()
var history = [table]
for key in operations {
    if key < 0 {
        table.removeValue(forKey: -key)
    } else {
        table[key] = Row()
    }
    history.append(table)
}
let height = table.height  // 2

let shape = RootedTree(table)
let root = shape?.root  // [55]
