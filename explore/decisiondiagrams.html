Decision diagrams

How do you store a Boolean function of many variables without writing out its whole truth table?

Example: a & b | c & d. The diagram tests a, and when a is false it skips b and tests c straight away. Its last test, of d, is the very vertex the earlier formula c | d built, because the shared table never makes the same test twice.

Formula 0 of 6

A decision diagram is a Boolean function drawn as a graph of tests, each asking one variable, in a fixed order. It merges any two tests that ask the same thing and lead the same way, and drops any test whose answer doesn’t matter. That leaves exactly one diagram per function.

What it’s forFunctions you can compare and count

A reduced ordered binary decision diagram stores a Boolean function so that equal functions are stored identically: checking whether two circuits do the same thing becomes comparing two numbers. It also counts the assignments that make a function true, finds one, and combines functions with any operator. Hardware verification, model checking, configuration solvers and access-control analysis all depend on it.

The ideaA decision tree, with the duplicates merged

Start from the full decision tree that asks every variable in a fixed order, a then b then c, with true or false at the leaves. Then apply two rules until nothing changes: merge any two tests that ask the same variable and lead to the same places, and remove any test whose two answers lead to the same place. What is left is the function’s unique diagram (Bryant, 1986).

GrafluentCollections keeps every function in one shared table, so a test that one formula builds is reused by every later formula that needs it. The tinted vertices above are those reuses. The table’s graphView is the graph drawn here, and any Grafluent algorithm can run over it.

Where it breaksOrder matters, sometimes enormously

The size of a diagram depends on the variable order. Some functions are tiny in one order and exponentially large in another, and a few, like integer multiplication, are large in every order. Choosing a good order is hard in general. When it goes badly, SAT solvers, which never build the whole function, often do better.

In SwiftThe formulas above, in GrafluentCollections

import DecisionDiagrams

/// A Boolean formula over variables numbered from 0.
indirect enum Formula: Equatable {
    case variable(Int)
    case not(Formula)
    case and(Formula, Formula)
    case xor(Formula, Formula)
    case or(Formula, Formula)
}

let formulas: [Formula] = [.and(.variable(0), .variable(1)), .or(.variable(2), .variable(3)), .or(.and(.variable(0), .variable(1)), .and(.variable(2), .variable(3))), .and(.xor(.variable(0), .variable(1)), .xor(.variable(2), .variable(3))), .xor(.xor(.xor(.xor(.variable(0), .variable(1)), .variable(2)), .variable(3)), .variable(4)), .or(.not(.and(.variable(0), .variable(1))), .variable(4))]

var diagram = BinaryDecisionDiagram(variableCount: 5)
func build(_ formula: Formula) -> BinaryDecisionDiagram.Function {
    switch formula {
    case .variable(let index): diagram.variable(index)
    case .not(let f): diagram.not(build(f))
    case .and(let f, let g): diagram.and(build(f), build(g))
    case .xor(let f, let g): diagram.xor(build(f), build(g))
    case .or(let f, let g): diagram.or(build(f), build(g))
    }
}
var functions: [BinaryDecisionDiagram.Function] = []
var tableBefore: [Int] = []
for formula in formulas {
    tableBefore.append(diagram.tableVertexCount)
    functions.append(build(formula))
}
let vertices = diagram.tableVertexCount  // 38
